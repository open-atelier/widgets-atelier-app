# Widgets Atelier

Decorative iOS Lock Screen widgets rendered from original SVG artwork, in the
`accessoryRectangular` and `accessoryCircular` families.

| | |
| --- | --- |
| App | `openatelier.widgets` |
| Widget extension | `openatelier.widgets.widgets` |
| Apple account | Free personal team — no paid account needed |
| Distribution | Personal device only, sideloaded |
| iOS | 17.0 and later |
| Data | None. Fully static. |

## Why the widgets are Swift, not TypeScript

Expo's `expo-widgets` builds widgets from TypeScript, but its plugin requires an
App Group, which is how the app pushes snapshots to the widget. **Free personal
teams cannot provision App Groups.** The entitlement is not available, and
requesting one breaks signing.

These widgets are entirely static, so the app and the widget never exchange
anything — layouts and artwork both live inside the extension binary. A plain
WidgetKit `StaticConfiguration` is therefore both sufficient and simpler, and it
needs no entitlements at all.

So the widget UI is hand-written SwiftUI under `targets/`, turned into an Xcode
target by [`@bacons/apple-targets`](https://github.com/EvanBacon/expo-apple-targets).
The Expo app is a thin host: the extension has to be embedded in an app, and it
gives somewhere to grow later. It does no work at runtime.

`expo-widgets` is deliberately not installed — that is the App Group problem
above, and it applies to the widgets only.

`@expo/ui` *is* used, for the host app. It has no entitlement requirements, so
none of that reasoning applies to it. The app is iOS-only and built from real
SwiftUI: native tabs, grouped `Form` sections, native pickers and SF Symbols
via `expo-symbols`.

## Layout

```
app/                           expo-router host app
  _layout.tsx                  native tabs
  (gallery)/                   every illustration, both variants
  (settings)/                  theme, instructions, licences
components/                    theme provider, design table, gallery row
artwork/                       source of truth: original SVGs
tools/svg-to-pdf.sh            artwork/*.svg -> the widget's asset catalog
targets/widgets/
  expo-target.config.js        target definition; no entitlements block
  Info.plist
  WidgetsAtelierBundle.swift   @main WidgetBundle — one row per picker entry
  Designs/                     one file per widget
  Shared/                      timeline provider and the shared art view
  Assets.xcassets/             generated PDFs, committed
```

`ios/` is generated by prebuild and gitignored. It must stay reproducible from
`app.json` plus `targets/` alone, because CI regenerates it from scratch. Never
hand-edit it.

## Running it

```sh
bun install
bun run artwork          # only when artwork/ changed; needs `brew install librsvg`
bunx expo prebuild --clean -p ios
bunx expo run:ios --device
```

For on-device signing, open `ios/WidgetsAtelier.xcworkspace` and select your
personal team on **both** the `WidgetsAtelier` and `WidgetsAtelierWidgets`
targets. You can put the team id in `app.json` as `ios.appleTeamId` to have
prebuild set it for you; without it the apple-targets plugin prints a warning,
which is harmless for simulator builds.

Then add a widget: **press and hold the Lock Screen → Customize → Lock Screen →
tap the widget area → Widgets Atelier**.

### If something goes wrong

- **Widget missing from the picker** — the extension was not embedded. Check the
  app target's *Frameworks, Libraries, and Embedded Content* in Xcode.
- **Blank or letterboxed widget** — a design is missing
  `.containerBackground(.clear, for: .widget)`. It is applied centrally in
  `Shared/AccessoryArt.swift`, so this only bites a design that bypasses it.
- **Signing failure** — confirm the extension has its own bundle id, that the
  personal team is selected on both targets, and that no entitlements file was
  generated for the extension.

## Artwork

**The `cat-*` and `sparkle` SVGs are placeholders.** They are correct in form —
flat filled paths, monochrome, tight viewBox — so the pipeline is proven end to
end, but they are not the intended art. Replace them and re-run `bun run
artwork`. `cat.svg` is real artwork (SVG Repo).

WidgetKit cannot render SVG, so `tools/svg-to-pdf.sh` converts each file to a
vector PDF and writes it into `targets/widgets/Assets.xcassets/<name>.imageset/`
with `preserves-vector-representation` and a `template` rendering intent. The
SVGs stay the source of truth; the PDFs are committed so a clean clone builds
without a converter installed.

Adding a design is three steps: drop the SVG in `artwork/`, run `bun run
artwork`, and add a `Widget` in `Designs/` plus a line in
`WidgetsAtelierBundle.swift`. Four to six designs is a comfortable ceiling —
each one is a separate row in the iOS picker.

**[docs/adding-an-illustration.md](docs/adding-an-illustration.md)** walks
through it properly, with a worked example, how to pick padding for a circular
slot, and what to check when a new design does not show up.

### What the artwork has to be

Accessory widgets render in `WidgetRenderingMode.vibrant`, which means:

- **Colour is discarded.** iOS desaturates the widget and recomposites it as a
  vibrant material over the wallpaper. Design in luminance and alpha only.
- **Black becomes transparent, white becomes opaque.** Mid-greys land in
  between. Use *alpha* rather than grey values to express depth.
- **The slots are small.** `accessoryCircular` is roughly 72–76pt across;
  `accessoryRectangular` is roughly 160×72pt. Hairlines and detail below a few
  points disappear. Bold closed shapes survive; delicate whiskers do not.

So each SVG should be flattened to filled paths (convert strokes to outlines),
monochrome, free of text elements (convert text to paths), and tightly cropped
with an explicit `viewBox` so `scaledToFit` behaves predictably.

Line art can stay as long as it is thick enough to survive. `cat.svg` is
stroke-style art flattened to filled paths; at `padding: 4` its median feature
is 6pt and only 6% of its strokes fall under 3pt. The rule exists to catch
hairlines, not to ban thin work. Do set the fill or stroke colour explicitly,
though — art left on `currentColor` or a dark brand colour converts to black,
which still works as a template but reads as a mistake next to the rest of
`artwork/`.

One SVG can often serve both families, but a rectangular composition rarely
reads well cropped to a circle — expect most designs to need a dedicated
circular variant.

### Checking a design

Xcode previews and the Simulator approximate vibrancy but do not reproduce it.
Check every design on the physical device Lock Screen:

- [ ] Light wallpaper
- [ ] Dark wallpaper
- [ ] Busy photographic wallpaper — the worst case for legibility
- [ ] Both Lock Screen widget slots
- [ ] Always-on display, if the device supports it

## Builds from CI

Two workflows, both `workflow_dispatch` only, both producing an **unsigned**
`.ipa` published as a prerelease:

| Workflow | Config | Bundle id | For |
| --- | --- | --- | --- |
| `build-unsigned-ios.yml` | Release | `gh.openatelier.widgets` | Installing and using |
| `build-unsigned-ios-dev.yml` | Debug | `gh.dev.openatelier.widgets` | Attaching a dev server |

A free account has no distribution certificate and no App Store Connect API key,
so CI cannot sign — **Sideloadly or AltStore signs at install time** with your
Apple ID, re-signing the embedded extension along with the app.

Each namespaces the app id so its builds install alongside a locally built copy
and alongside each other. The widget target derives its own id from the app's
using the plugin's leading-dot form (`bundleIdentifier: ".widgets"`), so the pair
stays in sync through that rename automatically. This matters more than it
looks: an extension whose id is not a prefixed child of its host app's does not
fail loudly, it just never appears in the picker.

The dev client build carries `expo-dev-client` and embeds no JS bundle — it
opens the launcher so you can connect to `bunx expo start`. Note that it only
reloads the host app's JavaScript. The widgets are native, so changing anything
under `targets/` still needs a full rebuild; the dev client buys you nothing
there.

Both workflows fail the build if the extension id is wrong, if any generated
entitlements file requests something a free account cannot provision, or if the
packaged IPA does not contain exactly one correctly-prefixed WidgetKit
extension. That last check exists because a widget-less IPA installs perfectly
and fails silently.

They also re-run `tools/svg-to-pdf.sh` before prebuild and warn if the committed
PDFs were stale. Conversion pins `SOURCE_DATE_EPOCH`, so unchanged artwork
converts to byte-identical PDFs and that warning means the artwork really did
change.

## Sideloading, and the 7-day expiry

Free personal team certificates last **7 days**. After that the app stops
opening and the widgets go blank, and it has to be re-installed.

- **AltStore** — can refresh automatically over Wi-Fi, but needs its companion
  app running on a computer on the same network.
- **Sideloadly** — simpler, but every refresh is manual.

Two other limits worth knowing: a free account allows about **10 App IDs per 7
days**, and the app and extension are two separate ids, so each install cycle
consumes two — avoid churning the bundle id during development. And only **3
sideloaded apps** can be installed at once.

## Constraints this project is built around

No App Groups, no push, no associated domains — the generated entitlements files
must stay empty. There is no App Store review, so no Guideline 4.2 concern; the
host app can stay minimal.

If you ever move to a paid account, revisiting `expo-widgets` is reasonable.
